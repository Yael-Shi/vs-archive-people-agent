# Architecture

Current structure of the standalone people pipeline. Field-level artifact contracts live in `docs/contracts.md`. Decision history lives in `docs/decision-log.md`.

## Purpose

`people-agent` is a read-only pipeline for VS Archive people work. The first slice is:

```text
discover -> freeze-evidence -> resolve -> identity review package
```

It selects changed documents, freezes mention evidence, matches those mentions to a production identity snapshot, and packages identity review. It does not apply anything to production.

## Repository boundary

### vs-archive

`/home/yshif/vs-archive/vs-archive` owns Django models, production state, export primitives, and the eventual preflight, backup, apply, and verify path. Production writes stay there.

### people-agent

This repository owns discovery, evidence freezing, identity resolution, identity-review packaging, the schemas for its artifacts, provenance, and checkpoint orchestration. Later research and review logic belong here too.

There is no Django import, no production database connection, and no AWS client. Production state is not inferred from a local database. The historical people-agent workspace is not the design to copy.

## Artifact boundary

`vs-archive` and `people-agent` meet through versioned JSON artifacts.

External snapshots, produced outside this package:

- document-text snapshot
- identity snapshot

Generated artifacts, produced and stamped here:

- discovery selection
- mention proposals (`mention-proposals-v1`)
- evidence package
- resolution report
- identity-review package
- run checkpoint

Exact fields are in `docs/contracts.md`. Generated artifacts carry provenance and a logical content hash. External snapshots are bound by file hash. They are not checked as if they were generated by this package.

## Displayed evidence

A title is metadata, not evidence. Eligible bodies are the displayed OCR transcription, displayed source text, displayed Hebrew translation, and manual-text body. Identical raw strings may share one body with more than one role. A whitespace-only difference stays a separate body. The displayed-text hash is what discovery uses to decide that content changed.

## Mention proposals and freeze-evidence

`freeze-evidence` does not find person names. The v1 command still reads a loose proposal list, or an object with a `mentions` array, and checks those proposals against the displayed body. It publishes an immutable evidence package. It does not discover names, assign production identity, or write production data.

`mention-proposals-v1` is a separate generated artifact. `package-mention-proposals` publishes it from human geometry: offsets and an optional `surface_kind`. The command derives `exact_mention`, `name_surface`, `title_surface`, and `evidence_snippet` from the displayed body, then orders mentions by archive item, evidence source, and outer offsets before stamping. It inserts the `human-authored` detector, leaves `identity_snapshot_file_sha256` null, and does not call a provider. Automated `find-mentions` is not implemented. `freeze-evidence` does not read `mention-proposals-v1`. Artifact validation rejects a duplicate outer span, an outer span with more than one line break, and a `surface_kind` that contradicts the title slice.

v1 evidence, resolution, review, and `run-checkpoint-v1` are unchanged. `RUN_STEPS` remains `discover -> freeze-evidence -> resolve -> review`.

## Mention identity

`mention_key` (`M0001` and so on) is a label for one run. `mention_fingerprint` is the durable identity of one occurrence. The fingerprint is the SHA-256 of the archive item, evidence source, source-text hash, and the start and end offsets. Offsets are zero-based Python code-point offsets into that displayed body. The slice `body_text[start_offset:end_offset]` must equal `exact_mention` with no whitespace rewrite. `occurrence_index` is display order derived from those offsets. A caller-supplied key, fingerprint, or index is discarded.

## Identity resolution

A deterministic match is an exact normalized hit on exactly one production `Person.name` or existing `PersonAlias.name`. Normalization is NFKC, casefold, and whitespace collapse. There is no fuzzy match and no title stripping. Confidence is stored and never chooses a class. Pending rows and local candidates are not production identity. A shared normalized name stays ambiguous.

## Review boundary

Deterministic existing-person matches are recorded as auto-resolution proposals. Ambiguous matches, new-person candidates, inferred aliases, and explicit identity-changing actions are human-review rows. The identity-review package is not an apply artifact. Nothing in it is an approved production write.

## Provenance and hashes

A logical content hash identifies the semantic body of a generated artifact. A physical file hash identifies the published bytes, including timestamp and producer. A child binds a generated parent by the parent's logical hash and may also record that parent's file hash for audit. Plain external inputs that affect an output are bound the same way: the evidence package records `mention_proposals_file_sha256`, and the resolution report records `local_candidates_file_sha256` (null when no file was supplied). Those hashes do not replace the frozen mentions or the resolution rows. Audit-only file hashes do not change the child's logical hash. On consumption, a generated artifact is schema-checked and its stored logical hash is recomputed. A mismatch fails closed. External snapshots are not given that logical-hash check.

## Run and checkpoint model

The only progression is `discover -> freeze-evidence -> resolve -> review`. Python `RUN_STEPS` owns that order. The checkpoint schema enum only lists the allowed step strings. Each checkpoint is a new file. Partial checkpoints are same-run resume state. Only a review-complete checkpoint is previous-run discovery memory, and it need not share the new `run_id`. Artifacts consumed inside the current run must share that run's `run_id`.

## Publication semantics

Outputs are immutable. Publishing a path that already exists fails. The writer finishes and fsyncs a temporary file in the destination directory, then `os.link`s it onto the destination. The link fails if the name exists, so a concurrent publisher cannot replace it. The temporary name is removed. The parent directory is fsynced after the link. A partial file is not published under the destination name.

## Error model

Contract failures are controlled `ArtifactError` values. The CLI prints structured `BLOCKED` JSON and a nonzero exit code. Codes in use:

- malformed artifact, including invalid JSON
- artifact read error, for a missing, unreadable, or non-UTF-8 input
- artifact exists
- input hash changed
- missing bound input
- unsupported schema version
- logical hash mismatch
- run-id mismatch
- incomplete prior checkpoint, when discovery is given a resumable checkpoint that has not finished review

Individual validation sentences are not part of this summary.

## Current non-goals

- automated mention finding. `package-mention-proposals` publishes `mention-proposals-v1` from human geometry. It is outside `RUN_STEPS`. An isolated Gemini mention pilot can propose surface spans for one displayed body. The pilot is not a pipeline step and not a versioned artifact. See `docs/gemini-mention-pilot.md`. Automated `find-mentions` is not implemented.
- historical or internet research
- biographies
- tagging
- production apply
- AWS or database mutation

## Future extension points

Not implemented: automated `find-mentions`, the mention-proposal diagnostics sidecar, evidence-package-v2, resolution-report-v2, identity-review-package-v2, run-checkpoint-v2, research, human decision artifacts, biography review, an approved apply package, and the main-repository apply and verify workflow that would consume that package. The Gemini mention pilot does not fill that gap. `package-mention-proposals` publishes `mention-proposals-v1` only.
